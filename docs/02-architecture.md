# 02 · Architecture

## 1. System overview

```
                 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
                 │  Web (React) │   │ Android (Kt) │   │  iOS (Swift) │
                 └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
                        │  HTTPS JSON (OpenAPI contract)      │
                        └───────────────┬─────────────────────┘
                                ┌───────▼────────┐
                                │     nginx      │  TLS, static web, /media, rate limits
                                └───────┬────────┘
                         ┌──────────────▼──────────────┐
                         │  anylo-api (uvicorn, N wkr) │  FastAPI
                         └──────┬───────────────┬──────┘
                                │               │ enqueue jobs
                     ┌──────────▼───┐   ┌───────▼─────────┐
                     │ PostgreSQL 16│◄──┤ anylo-worker    │  WhatsApp, PDFs, exports,
                     │ (RLS)        │   │ (1 process)     │  subscription sync, snapshots
                     └──────────────┘   └───────┬─────────┘
                                                │
                    External: Razorpay · OpenAI · WhatsApp Cloud API · SMTP
```

- **One backend** serves all clients. No Docker. Processes run under systemd (`16-deployment-vps.md`).
- **PostgreSQL** is the only stateful store. The job queue is a Postgres table, so there is no Redis in v1.
- **Media** (product photos, logos, generated PDFs/XLSX) lives on local disk under `MEDIA_ROOT`. It is served by nginx: product and logo images through `X-Accel-Redirect` checks, and generated documents through signed short-lived URLs. The storage interface is designed so it can move to S3-compatible storage later.

## 2. Backend layout

```
backend/
  app/
    main.py              # app factory, routers, middleware, lifespan (no background loops)
    config.py            # pydantic-settings, all env vars
    database.py          # engines, rls_session(), privileged_session()
    deps.py              # auth + role + subscription dependencies
    errors.py            # AppError(code, detail, status) + handlers
    models/              # SQLAlchemy 2.0 mapped classes, one file per aggregate
    schemas/             # Pydantic v2 request/response models
    routers/             # thin HTTP layer: validate → call service → shape response
    services/            # business logic (billing, gst, stock, reports, ai, subscription…)
      gst/               # tax engine (pure functions, heavily tested)
      reports/           # report queries + xlsx builders
      ai/                # OpenAI client, tool registry, prompts
      whatsapp/          # Cloud API client, templates, sender
      payments/          # Razorpay client + webhook handling
    worker/
      main.py            # `python -m app.worker.main` – job loop
      jobs/              # one module per job type
    scripts/             # create_admin, rls_check, seed_demo
  alembic/
  tests/
```

**Rules**
- **Routers** don't hold business logic. They parse input, call a service, and return a schema.
- **Services** take a `Session` and an `Actor` (user id, role, shop id) and raise `AppError`. They never import FastAPI.
- **The GST engine** (`services/gst/`) is pure: Decimal in, Decimal out, no DB access. It can be used by the API, by tests, and later by a client-side preview.

## 3. Request lifecycle

1. nginx terminates TLS and applies a per-IP rate limit to `/auth/*`.
2. Middleware assigns a request id, enforces the body-size limit, and adds security headers.
3. The `get_actor` dependency:
   - decodes the access JWT (`sub`, `sid` = session id, `ver` = token version);
   - loads the user in a privileged lookup and checks `is_active` and the token version;
   - resolves the shop and its subscription state.
4. The `rls_session(actor)` dependency opens a transaction and runs `set_config` for:
   - `app.role`
   - `app.user_id`
   - `app.shop_id`
5. Guard dependencies run:
   - `require_roles(...)`
   - `require_writable_subscription()` for mutating requests (`10-subscription-razorpay.md`)
6. The service does its work. On success the transaction commits; on any exception it rolls back.
7. The response passes through: money serialized as strings, timestamps as ISO-8601 UTC.

## 4. Multi-tenancy (RLS)

| GUC | Values |
|---|---|
| `app.role` | `admin`, `support`, `owner`, `manager`, `salesperson`, `system` |
| `app.user_id` | uuid |
| `app.shop_id` | uuid or `''` |

The standard tenant policy (generated by a helper used in every migration):

```sql
CREATE POLICY tenant_isolation ON <table>
USING (
  current_setting('app.role', true) IN ('admin','system')
  OR shop_id = NULLIF(current_setting('app.shop_id', true), '')::uuid
  OR (current_setting('app.role', true) = 'owner'
      AND shop_id IN (SELECT so.shop_id FROM shop_owners so
                      WHERE so.owner_id = NULLIF(current_setting('app.user_id', true), '')::uuid))
)
WITH CHECK (<same>);
```

- `support` is added to the first branch on non-PII tables only. PII tables (`customers`, `ai_messages`) exclude it.
- Child tables without `shop_id` (for example `invoice_lines`) get a `shop_id` column anyway. Duplicating it keeps policies simple and indexes effective.
- The `system` role is used only by the worker and webhooks.

## 5. Background jobs

The `jobs` table holds: `id, kind, payload jsonb, run_at, attempts, max_attempts, status, last_error, locked_at, locked_by`.
- Producers insert a job row **in the same transaction** as the business change (outbox pattern).
- The worker loop runs `SELECT … WHERE status='queued' AND run_at <= now() ORDER BY run_at FOR UPDATE SKIP LOCKED LIMIT 10`, then executes the jobs. Retries use exponential backoff.

| Job kind | Trigger |
|---|---|
| `whatsapp.send_invoice` | invoice created with auto-send on |
| `pdf.render_invoice` | on demand / WhatsApp |
| `export.report_xlsx` | large exports (> 5k rows) run async; small ones stream directly |
| `subscription.sync` | Razorpay webhook received / nightly reconcile |
| `finance.daily_close` | 23:59 shop time: closing cash and daily snapshot |
| `stock.low_stock_alert` | after stock movement crosses reorder level |
| `ai.summarize_week` | Monday 08:00: weekly digest notification |

The scheduler is a small table of cron rows (`scheduled_tasks`) that the worker evaluates every minute. There is no external cron.

## 6. Clients

- **Web:** a single React app with three shells, chosen by role:
  - `/pos` for counter billing
  - `/app` for the shop back office and owner views
  - `/admin` for the platform
- **Android:** a single-activity Compose app with shells by role (see `14-android.md`).
- **iOS:** SwiftUI with the same shells (see `15-ios.md`).
- **API types:**
  - Web generates TS types from `/openapi.json` with `openapi-typescript`.
  - Android and iOS hand-write DTOs, verified by contract tests against the schema snapshot `backend/openapi.snapshot.json`, which CI regenerates and diffs.

## 7. Configuration

All configuration is in env vars (`backend/.env`), loaded by `app/config.py`:

| Group | Vars |
|---|---|
| Database | `DATABASE_URL` (app role), `DATABASE_URL_OWNER` (migrations) |
| Auth | `JWT_SECRET`, `ACCESS_TOKEN_MINUTES=15`, `REFRESH_TOKEN_DAYS=30` |
| URLs | `PUBLIC_WEB_URL`, `PUBLIC_API_URL`, `CORS_ORIGINS` |
| Media | `MEDIA_ROOT`, `MEDIA_SIGNING_SECRET` |
| Razorpay | `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `RAZORPAY_PLAN_ID` |
| OpenAI | `OPENAI_API_KEY`, `OPENAI_MODEL`, `OPENAI_MODEL_DEEP`, `AI_MONTHLY_QUOTA_PER_SHOP` |
| WhatsApp | `WHATSAPP_ENABLED`, `WHATSAPP_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_APP_SECRET`, `WHATSAPP_VERIFY_TOKEN` |
| Email | `SMTP_*` (password reset, subscription mails) |
| Business rules | `TRIAL_DAYS=30`, `GRACE_DAYS=7` |
| Platform identity | `PLATFORM_GSTIN`, `PLATFORM_LEGAL_NAME`, `PLATFORM_STATE_CODE` (for our own subscription invoices) |
